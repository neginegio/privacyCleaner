# Word匿名化v1 設計

## 目的

hoso Privacy Cleanerに、Word文書をローカルで検査し、利用者確認後に匿名化済み`.docx`を出力する機能を追加する。

PDF Generation3の評価結果を踏まえ、Word v1ではOCR、座標矩形、ページ画像処理を使わない。Word内部の文字情報と文書構造を直接扱い、書式保持と未対応領域の明示を優先する。

## 対象範囲

対象ファイルは`.docx`のみとする。

v1で匿名化処理する領域は次の範囲に限定する。

- 通常段落
- 表
- 表セル
- ヘッダー
- フッター

v1で最低限扱う匿名化対象カテゴリは次のとおり。

- 会社名
- 氏名
- 住所
- 電話番号
- メールアドレス
- 銀行名

検出と置換の基本方針は、既存Excel機能の`JapanesePresidioDetector`、`AliasBook`、`ProcessingOptions`、`replacement_for`を再利用する。ただし、Wordでは段落、run、表セル、ヘッダー、フッターなどの構造に分かれるため、Excel列見出し前提のルールはそのまま適用せず、Word固有の文脈で検証する。

## 対象外

v1では次の領域を匿名化処理対象外とする。

- `.docm`
- テキストボックス
- 図形内文字
- コメント
- 脚注
- 文末脚注
- 変更履歴
- 埋め込みオブジェクト内文字
- 複雑なフィールドコード

これらを文書内で検出した場合は、「未対応領域あり」として検査結果、処理報告書、監査記録へ記録する。

## 安全制御

外部共有用では、未対応領域が存在する場合に最終出力を停止する。利用者が画面上で本文だけ確認しても、未対応領域に元識別情報が残る可能性があるためである。

分析継続用では、未対応領域が存在する場合に明確な警告を表示したうえで出力を許可する案とする。ただし、実装前に既存Excelの分析継続用方針と整合性を確認する。特に、分析継続用でも外部共有へ転用される可能性があるため、警告文と処理報告書には「未対応領域内の匿名化は保証しない」ことを明記する。

未確認候補が残っている場合は、既存Excel/PDFと同様に最終出力を停止する。承認、解除、手動修正が完了した候補だけを変換対象とする。

## Word内部構造の扱い

`.docx`はOpen Packaging Convention形式のZIPパッケージとして扱う。v1の主処理は`python-docx`を第一候補とし、通常段落、表、表セル、ヘッダー、フッターの高水準操作に使う。

一方、`python-docx`だけでは検出や安全確認が不足する領域があるため、標準ライブラリの`zipfile`とXML解析による内部検査を併用する。ライブラリ追加は実装開始時に別途判断し、設計固定段階では追加しない。

ハイパーリンクは次の方針とする。

- 表示文字は検査対象とする。
- リンク先URLも検査対象とする。
- URLの削除、置換、維持の詳細は実装時に安全性を検討する。

文書プロパティは、作成者、最終保存者、会社名などの個人情報・機密情報が入る可能性があるため、v1で少なくとも検査対象とする。`python-docx`で安全に削除または置換できるプロパティと、内部XML直接処理が必要なプロパティを実装時に切り分ける。

## 匿名化候補の識別方式

PDFの座標矩形方式はWordでは使わない。候補はWord内部の構造位置で識別する。

候補位置には次の情報を持たせる。

- story種別: `body` / `header` / `footer`
- section index
- header/footer種別: default / first_page / even_page
- table index
- row index
- cell index
- paragraph index
- run index
- run内文字オフセット
- 候補開始オフセット
- 候補終了オフセット

通常段落では、story種別、section index、paragraph index、run index、文字オフセットを主キーにする。

表セルでは、story種別、section index、table index、row index、cell index、cell内paragraph index、run index、文字オフセットを主キーにする。

ヘッダー/フッターでは、story種別、section index、header/footer種別、paragraphまたはtable内位置を主キーにする。

同じ文字列が複数箇所に存在しても混同しないよう、候補IDは構造位置、情報種別、正規化済み候補文字列のHMAC-SHA256から生成する。HMAC鍵管理はPDFレビュー状態保存の設計を再利用するが、Word向けschema名を分ける。

## 書式保持方針

Word匿名化では、単純に`paragraph.text`を書き換えるとrun単位の書式が失われる可能性がある。そのため、v1ではrunを基本単位として置換する。

単一run内に候補が収まる場合は、そのrunのテキストだけを部分置換し、太字、フォント、サイズ、色、下線などのrun書式を維持する。

候補文字列が複数runにまたがる場合は、次の方針を検討する。

- 先頭runに置換後文字列を入れる。
- 後続runから候補範囲に該当する文字を削除する。
- 先頭runの書式を代表書式として採用する。
- 置換後に空runが残る場合は、構造破壊を避けるため原則としてrun自体は削除せず空文字にする。

ハイパーリンク内のrunを置換する場合は、リンク表示文字とリンク先URLを別々に扱う。リンク表示文字のみ置換してURLに元情報が残る状態を避けるため、URL検査結果も出力可否判定に含める。

表セルはセル書式、罫線、背景色を維持する。セル単位での値丸ごと置換は、セル内の複数段落やrun書式を壊しやすいため、v1では段落/run単位の置換を優先する。

## 内部残存検査

匿名化後`.docx`について、画面上の本文だけでなくパッケージ内部に元識別情報が残っていないか検査する。

最低限検査する対象は次のとおり。

- `word/document.xml`
- `word/header*.xml`
- `word/footer*.xml`
- `word/_rels/*.rels`
- `_rels/.rels`
- `docProps/core.xml`
- `docProps/app.xml`
- `docProps/custom.xml`
- `word/comments*.xml`
- `word/footnotes.xml`
- `word/endnotes.xml`
- `word/settings.xml`
- その他テキストを保持し得る`.xml`と`.rels`

外部共有用では、匿名化対象の原文が内部XMLに残存している場合は出力不可とする案を採用する。分析継続用では、残存が検出された場合に強い警告を出し、処理報告書に残存候補のXML部品名を記録する。ただし、原文そのものを報告書へ大量に出さないようにし、必要に応じてHMACや短い分類情報で記録する。

未対応XMLに文字列が存在するだけでは即座に個人情報とは限らないため、検出対象原文との照合と未対応領域の存在検査を分ける。

## テストデータ分割

実装前にWordテストデータを3群へ分離する。

### A. 開発用Word

検出ルールや置換ロジックの開発に使用してよい。典型的な段落、表、ヘッダー、フッター、複数run分割、同一語の複数出現を含める。

### B. 検証用Word

回帰テストと性能確認に使用する。開発中の細かなルール調整へ過度に利用しない。開発用Wordで作ったルールが、別構造でも機能するかを見る。

### C. 完全ホールドアウトWord

実装・調整中は内容を利用しない。最終評価時にのみ初回スキャンを実行し、結果を固定する。完全ホールドアウトの正解データは候補生成コードから参照できない場所と形式で管理する。

各群はファイル単位で固定し、設定ファイルにdataset version、用途、対象ファイル名、SHA-256を記録する。正解データ、候補生成結果、レビュー状態を候補生成ロジックへ渡すことは禁止する。

## 最初の合成テスト案

最初の合成テストWordには、少なくとも次を含める。

- 通常段落の会社名
- 通常段落の氏名
- 通常段落の住所
- 電話番号
- メールアドレス
- 銀行名
- 表セルの会社名
- 表セルの氏名
- ヘッダーの会社名
- フッターの氏名
- 1つの対象文字列が複数runに分割されたケース
- 同じ会社名が複数箇所に存在するケース
- 匿名化してはいけない一般文章
- 未対応テキストボックスを含むケース
- 未対応コメントを含むケース

期待結果は実装前に固定する。期待結果には、候補数、カテゴリ、構造位置、変換後文字列、未対応領域検出、出力可否を含める。

## 評価方法

評価指標はPDF評価の反省を踏まえ、候補生成と正解データを分離したうえで算出する。

- `ground_truth_count`: 正解候補数
- `candidate_count`: 初回候補数
- `matched_ground_truth_count`: 候補が一致した正解数
- `missed_ground_truth_count`: 見逃し数
- `true_positive_candidate_count`: 正解に対応する候補数
- `false_positive_candidate_count`: 誤検出候補数
- `recall`
- `candidate_precision`

WordではPDFの矩形被覆率は使わない。代わりに、構造位置一致、文字範囲一致、カテゴリ一致、置換後残存なしを評価する。

## 完全ホールドアウト方針

完全ホールドアウトWordは、ルール開発、原因分析、手動調整、デバッグに使用しない。初回評価の前に候補生成ルールを固定し、評価完了まで変更しない。

禁止事項は次のとおり。

- 正解データを候補生成コードへ渡すこと。
- 固定ファイル名、固定段落番号、固定文字列に依存する候補生成を追加すること。
- 初回候補結果を見てから同じホールドアウト文書の評価前に検出ルールを調整すること。
- 正解文字列、原文、HMAC鍵、秘密情報をGit管理ファイルへ保存すること。

## 実装段階案

1. `.docx`構造インベントリを実装する。本文、表、ヘッダー、フッター、未対応領域、文書プロパティ、ハイパーリンクURLを検出する。
2. Word候補位置モデルを追加する。PDF座標ではなく構造IDで候補を追跡する。
3. 通常段落と表セルのスキャンを実装する。
4. ヘッダーとフッターのスキャンを実装する。
5. run単位の書式保持置換を実装する。
6. 未確認候補と未対応領域による出力停止を実装する。
7. 内部XML残存検査を実装する。
8. CSV、処理報告書、監査JSONを実装する。
9. 開発用Word、検証用Word、完全ホールドアウトWordの評価手順を固定する。
10. 完全ホールドアウト評価は、実装調整が終わってから一度だけ実行する。
