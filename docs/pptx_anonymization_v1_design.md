# PPTX匿名化v1 設計

## 目的

hoso Privacy Cleanerに、PowerPointスライド(`.pptx`)をローカルで検査し、利用者確認後に匿名化済み`.pptx`を出力する機能を追加する。

Word v1と同じくOCR、座標矩形、ページ画像処理を使わない。PPTX内部の文字情報と文書構造を直接扱い、書式保持と未対応領域の明示を優先する。

## 対象範囲

対象ファイルは`.pptx`のみとする。

v1で匿名化処理する領域は次の範囲に限定する。

- スライド上の図形(テキストフレームを持つ図形すべて。タイトル・本文などのプレースホルダーを含む)
- 表・表セル
- スピーカーノート
- グループ化された図形の内部(`python-pptx`で子図形へ再帰的に到達できるため)

v1で最低限扱う匿名化対象カテゴリは、Wordと揃えて次のとおりとする。

- 会社名
- 氏名
- 住所
- 電話番号
- メールアドレス
- 銀行名

検出と置換の基本方針は、既存の`JapanesePresidioDetector`、`GinzaEntityDetector`、`AliasBook`、`ProcessingOptions`、`replacement_for`を再利用する。ただし、検出ルール本体(正規表現・誤検出除外・候補選定ロジック)はWordの実装を直接共有せず、PPTX専用に新規作成する。Wordの正規表現ルールは実ホールドアウトデータでチューニング済みであり、地の文中心のWordに対してPPTXは箇条書き・短い断片テキストが中心という性質差があるため、共有モジュール化はWordの既検証挙動を意図せず壊すリスクがある。

## 対象外

v1では次の領域を匿名化処理対象外とする。

- グラフ(chart)
- SmartArt(`graphicFrame`内のdiagramデータ。`python-pptx`はテキストとして解析しない)
- 埋め込みOLEオブジェクト
- コメント
- スライドマスター・スライドレイアウトの固定テキスト(個々のスライドが継承するテンプレート側の文字。編集対象はスライド本体のみとする)
- アニメーション・トランジションに関連する情報

これらを文書内で検出した場合は、「未対応領域あり」として検査結果、処理報告書、監査記録へ記録する。

## 安全制御

Wordと同じ方針とする。

外部共有用では、未対応領域が存在する場合に最終出力を停止する。利用者が画面上で本文だけ確認しても、未対応領域(グラフのデータラベル等)に元識別情報が残る可能性があるためである。

分析継続用では、未対応領域が存在する場合に明確な警告を表示したうえで出力を許可する。警告文と処理報告書には「未対応領域内の匿名化は保証しない」ことを明記する。

未確認候補が残っている場合は、既存Excel/PDF/Wordと同様に最終出力を停止する。承認、解除、手動修正が完了した候補だけを変換対象とする。

## PPTX内部構造の扱い

`.pptx`はOpen Packaging Convention形式のZIPパッケージとして扱う。v1の主処理は`python-pptx`を第一候補とし、スライド、図形、テキストフレーム、表、スピーカーノートの高水準操作に使う。

`python-pptx`だけでは検出や安全確認が不足する領域(グラフのデータラベル、SmartArt等)があるため、標準ライブラリの`zipfile`とXML解析による内部検査を併用する。

Wordの「section」に相当する構造単位はPPTXには存在しない。代わりに「スライド番号」が構造の主軸になる。

図形の走査方針は次のとおり。

- `shape.has_text_frame`が真の図形は、テキストフレームの段落・runを検査対象とする(プレースホルダーかどうかは問わない)。
- `shape.has_table`が真の図形は、表の各セルのテキストフレームを検査対象とする。
- `shape.shape_type`が`GROUP`の図形は、`shape.shapes`で子図形へ再帰する。
- 上記いずれにも該当しない図形(グラフ、SmartArt等)は未対応領域として記録する。

スピーカーノートは`slide.has_notes_slide`が真の場合のみ`slide.notes_slide.notes_text_frame`を検査する。`has_notes_slide`を確認せずに`notes_slide`へアクセスすると、`python-pptx`が空のノートスライドを新規作成してしまう(副作用)ため、スキャン処理では必ず事前判定を行う。

文書プロパティ(`Presentation.core_properties`: author, last_modified_by, title, subject, keywords, comments等)は、Wordと同じく個人情報・機密情報が入る可能性があるため検査対象とする。

## 匿名化候補の識別方式

PDFの座標矩形方式はPPTXでも使わない。候補はPPTX内部の構造位置で識別する。

候補位置には次の情報を持たせる。

- slide index
- shape id・shape name
- container種別: `shape_text` / `table_cell` / `notes`
- プレースホルダー種別(プレースホルダーの場合のみ。タイトル/本文/その他)
- table row index・table column index(表セルの場合)
- paragraph index
- run index
- run内文字オフセット
- 候補開始オフセット
- 候補終了オフセット

通常図形テキストでは、slide index、shape id、paragraph index、run index、文字オフセットを主キーにする。

表セルでは、slide index、shape id、table row/column index、cell内paragraph index、run index、文字オフセットを主キーにする。

スピーカーノートでは、slide index、container種別(`notes`)、paragraph index、run index、文字オフセットを主キーにする。

候補IDは構造位置、情報種別、正規化済み候補文字列のHMAC-SHA256から生成する。HMAC鍵管理はWord/PDFレビュー状態保存の設計を再利用するが、PPTX向けschema名を分ける。

## 書式保持方針

Wordと同じくrunを基本単位として置換する。単純にパラグラフ全体のテキストを書き換えるとrun単位の書式(太字、フォント、サイズ、色等)が失われるためである。

単一run内に候補が収まる場合は、そのrunのテキストだけを部分置換し、run書式を維持する。

候補文字列が複数runにまたがる場合は、次の方針とする。

- 先頭runに置換後文字列を入れる。
- 後続runから候補範囲に該当する文字を削除する。
- 先頭runの書式を代表書式として採用する。
- 置換後に空runが残る場合は、構造破壊を避けるため原則としてrun自体は削除せず空文字にする。

表セルはセル書式・罫線・背景色を維持する。セル単位での値丸ごと置換は段落/run書式を壊しやすいため、v1では段落/run単位の置換を優先する。

## 内部残存検査

匿名化後`.pptx`について、画面上の本文だけでなくパッケージ内部に元識別情報が残っていないか検査する。

最低限検査する対象は次のとおり。

- `ppt/slides/slide*.xml`
- `ppt/slides/_rels/*.rels`
- `ppt/notesSlides/notesSlide*.xml`
- `ppt/notesSlides/_rels/*.rels`
- `docProps/core.xml`
- `docProps/app.xml`
- `docProps/custom.xml`
- `_rels/.rels`
- その他テキストを保持し得る`.xml`と`.rels`

外部共有用では、匿名化対象の原文が内部XMLに残存している場合は出力不可とする。分析継続用では、残存が検出された場合に強い警告を出し、処理報告書に残存候補のXML部品名を記録する。原文そのものを報告書へ大量に出さないようにし、必要に応じてHMACや短い分類情報で記録する。

未対応XMLに文字列が存在するだけでは即座に個人情報とは限らないため、検出対象原文との照合と未対応領域の存在検査を分ける。

## テストデータ分割

実装前にPPTXテストデータを3群へ分離する。

### A. 開発用PPTX

検出ルールや置換ロジックの開発に使用してよい。典型的なタイトル・本文・表・スピーカーノート、複数run分割、同一語の複数出現を含める。

### B. 検証用PPTX

回帰テストと性能確認に使用する。開発中の細かなルール調整へ過度に利用しない。開発用PPTXで作ったルールが、別構造でも機能するかを見る。

### C. 完全ホールドアウトPPTX

実装・調整中は内容を利用しない。最終評価時にのみ初回スキャンを実行し、結果を固定する。完全ホールドアウトの正解データは候補生成コードから参照できない場所と形式で管理する。

各群はファイル単位で固定し、設定ファイルにdataset version、用途、対象ファイル名、SHA-256を記録する。正解データ、候補生成結果、レビュー状態を候補生成ロジックへ渡すことは禁止する。

v1実装時点では実データ(dev/validation/holdout用の実PPTXファイル)が用意できていないため、評価手順・ツールの雛形のみを整備し、実際のdev/validation/holdout評価は実データ入手後に別途実施する。

## 最初の合成テスト案

最初の合成テストPPTXには、少なくとも次を含める。

- スライド本文図形の会社名
- スライド本文図形の氏名
- スライド本文図形の住所
- 電話番号
- メールアドレス
- 銀行名
- 表セルの会社名
- 表セルの氏名
- スピーカーノートの氏名
- 1つの対象文字列が複数runに分割されたケース
- 同じ会社名・氏名が複数スライドに存在するケース(エイリアス再利用の確認)
- 匿名化してはいけない一般文章
- 未対応領域(グラフ等)を含むケース

期待結果は実装前に固定する。期待結果には、候補数、カテゴリ、構造位置、変換後文字列、未対応領域検出、出力可否を含める。

## 評価方法

評価指標はWord評価を踏襲する。候補生成と正解データを分離したうえで算出する。

- `ground_truth_count`: 正解候補数
- `candidate_count`: 初回候補数
- `matched_ground_truth_count`: 候補が一致した正解数
- `missed_ground_truth_count`: 見逃し数
- `true_positive_candidate_count`: 正解に対応する候補数
- `false_positive_candidate_count`: 誤検出候補数
- `recall`
- `candidate_precision`

PDFの矩形被覆率は使わない。代わりに、構造位置一致、文字範囲一致、カテゴリ一致、置換後残存なしを評価する。

## 完全ホールドアウト方針

完全ホールドアウトPPTXは、ルール開発、原因分析、手動調整、デバッグに使用しない。初回評価の前に候補生成ルールを固定し、評価完了まで変更しない。

禁止事項は次のとおり。

- 正解データを候補生成コードへ渡すこと。
- 固定ファイル名、固定スライド番号、固定文字列に依存する候補生成を追加すること。
- 初回候補結果を見てから同じホールドアウト文書の評価前に検出ルールを調整すること。
- 正解文字列、原文、HMAC鍵、秘密情報をGit管理ファイルへ保存すること。

## 実装段階案

1. `.pptx`構造インベントリを実装する。スライド、図形、表、スピーカーノート、未対応領域、文書プロパティを検出する。
2. PPTX候補位置モデルを追加する。PDF座標ではなく構造IDで候補を追跡する。
3. スライド本文図形と表セルのスキャンを実装する。
4. スピーカーノートのスキャンを実装する。
5. run単位の書式保持置換を実装する。
6. 未確認候補と未対応領域による出力停止を実装する。
7. 内部XML残存検査を実装する。
8. CSV、処理報告書、監査JSONを実装する。
9. 合成テストPPTXでのエンドツーエンドテストを実装する。
10. 開発用PPTX、検証用PPTX、完全ホールドアウトPPTXの評価手順の雛形を用意する(実データ入手後に本実施)。
